## 1. 変更・追加する機能の説明

c8b038c のコードレビューで見つかった指摘（🔴1・🟡5・🟢3）を、すべて修正する。

背景：Dependency Check ウィンドウの**一番の目的**は、未登録の子アセットが「どこで（どのグループのどの親から）、どのくらい使われているか」を見て、Group の作成・設定（粒度の調整、更新頻度の違うものが同じ Group に混ざっていないかの確認）を見直す材料にすること。実際のビルドでどうなるかは**2番目に重要**（参考情報）で、正確な確認は Addressables 標準の Analyze に任せる。c8b038c の実装は、判定の仕組みはこの目的に合っているが、画面・出力・文書が「ビルドでの重複同梱を見つける機能」として書かれており、後から読む人が「ビルドで重複する」と誤解する。また、登録済みのアセットを経由した使用と直接の使用が区別できない。

主な内容：
- 「重複」「重複同梱」の表現を、「複数グループ」に改める（画面・テキスト出力・コードの名前・文書）。ビルドでの重複の判定ではないことを、注記と文書で明示する（🔴）
- 参照元を、親が子を**直接使っている**のか、登録済みのアセットを**経由して使っている**のかで区別し、経由は経由先を表示する（🟡）
- `Pack Separately` の印を「ビルド時の参考」の位置づけに弱める（削除はしない）（🟡）
- `Resources/` の印は残し、理由を「ビルドでの二重化の原因」から「登録の漏れ・移行の漏れの手がかり」に書き直す（🟡）
- `Packages/` 配下のサイズが常に 0 B になる問題と、サイズ取得で IO 以外の例外が走査を止める問題を直す（🟡）
- `OnGUI` のたびに全行を数え直している処理（複数グループの件数・高さの合計）を、表示行を作り直すときだけにする（🟡）
- README の古い記述（実装済みなのに「後者は予定」）・用語集のコード上の命名の誤り（`AccIsDuplicated`）・日時の書式のカルチャ指定・Runtime の型に関する書き方を直す（🟡・🟢）

今やる理由：本モジュールは UPM で他プロジェクトに配布する汎用モジュールで、Editor ウィンドウの表示・文書を読んだ人が、機能の目的を取り違えないようにしておく必要がある。

## 2. ユーザーストーリー

- Addressables のグループを組む開発者として、Group の作成・設定を見直すために、未登録のアセットが**どこでどのくらい使われているか**を、ビルドの結果と取り違えずに見たい
- 開発者として、Group を見直すときにどの親を動かすべきかを判断するために、参照元が子を**直接使っている**のか、登録済みの別のアセットを**経由している**のかを区別して見たい
- 開発者として、「複数グループ」の行がビルドで必ず重複するわけではないことを知るために、画面の注記と文書で、判定の意味とビルド結果の確認方法（Analyze）を読みたい
- 開発者として、ビルド時の参考情報（`Pack Separately`）も残してほしい。ただし、主な情報と混ざらないよう、位置づけが分かる形で見たい
- 開発者として、`Packages/` 配下のアセットも、サイズの大きい順の並べ替えに使えるよう、実際のサイズを見たい
- レビュアーとして、修正後も、ウィンドウが読み取り専用で、Editor アセンブリの中だけで完結していることを確認したい

## 4. 制約事項

- Editor 拡張は**読み取り専用**（CLAUDE.md「設計の絶対ルール」）。登録・グループ整理の自動化、手動 Release・強制回収のボタンを作らない
- 窓口（`IAddressableDebugReader`）・`AddressableManager` に触れない。機能フォルダの相互参照をしない
- 集約・整形（Unity 非依存のクラス）に Unity の型を持ち込まない。経由の判定は集約側で行う
- DI コンテナ・R3 に依存しない。UniTask を使わず、同期処理（`DisplayCancelableProgressBar`）で走査する
- 一時コレクションを描画のたびに確保しない。描画は IMGUI（既存の Editor コードと揃える）
- 設計仕様書 6章の過去の項目は書き換えない。新しい日付の項目として追記する
- 命名は `conventions.md` に従う（フィールド `_camelCase`・アクセサ `Acc`・引数とローカル `snake_case`・定数 `UPPER_SNAKE`）
- 画面の文字は日本語（既存のデバッグウィンドウに合わせる）
- CHANGELOG は更新しない（担当者の運用）。コードレビュー・手動検証・ドキュメントの最終確認は Claude の担当外
